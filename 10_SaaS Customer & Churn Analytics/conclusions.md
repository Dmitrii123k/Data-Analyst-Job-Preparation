# Итоговые выводы

## 1. Общая характеристика проекта

В рамках проекта проведён анализ SaaS-клиентов, подписок, поведения пользователей продукта, обращений в поддержку и событий оттока.

Основные задачи анализа:

* оценить клиентскую базу и подписки;
* определить уровень churn;
* выявить основные причины оттока;
* проанализировать churn по клиентским сегментам;
* оценить финансовое влияние оттока;
* изучить использование функций продукта;
* оценить эффективность службы поддержки;
* проверить статистические гипотезы о факторах, связанных с churn.

---

## 2. Основные бизнес-метрики

* Клиенты: **500**
* Подписки: **5 000**
* Активные подписки: **4 514**
* Churned customers: **110**
* Churn rate: **22.00%**
* Active MRR: **$10,159,608**
* Active ARR: **$121,915,296**
* Средний MRR на активную подписку: **$2,250.69**
* Суммарные возвраты по churn events: **$8,652.25**
* Reactivation rate: **10.17%**
* Средняя удовлетворённость клиентов: **3.98 / 5**
* Доля эскалаций обращений: **4.75%**

Важно: один клиент может иметь несколько churn events. Поэтому количество churned customers (**110**) не равно количеству churn events (**600**).

---

## 3. Анализ churn

Общий churn rate составляет **22.00%**.

При анализе тарифов существенных различий не обнаружено:

* Enterprise — **22.08%**
* Basic — **22.02%**
* Pro — **21.91%**

Таким образом, тарифный план не выглядит основным фактором клиентского оттока.

### Churn по отраслям

Наиболее высокий churn наблюдается в DevTools:

* DevTools — **30.97%**
* FinTech — **22.32%**
* HealthTech — **21.88%**
* EdTech — **16.46%**
* Cybersecurity — **16.00%**

Разница между DevTools и Cybersecurity составляет почти **15 процентных пунктов**.

При этом статистический тест χ² дал `p-value = 0.0657`. При уровне значимости 5% статистически значимая связь между отраслью и churn не подтверждается.

Следовательно, DevTools следует рассматривать как **направление для дальнейшего исследования**, но не как доказанный статистический фактор churn.

### Churn по странам

Наибольшие значения наблюдаются в следующих странах:

* Germany — **32.00%**
* United States — **23.37%**
* France — **22.73%**
* India — **20.41%**
* United Kingdom — **18.97%**
* Canada — **17.39%**
* Australia — **12.50%**

Однако χ²-тест не подтвердил статистически значимую связь между страной и churn (`p-value = 0.6588`).

## 4. Основные причины оттока

Наиболее распространённой **зарегистрированной причиной churn events** является `features`.

| Причина    | Churn events |  Доля |
| ---------- | -----------: | ----: |
| Features   |          114 | 19.0% |
| Budget     |          104 | 17.3% |
| Support    |          104 | 17.3% |
| Unknown    |           95 | 15.8% |
| Competitor |           92 | 15.3% |
| Pricing    |           91 | 15.2% |

Причины распределены достаточно равномерно. Ни одна причина не формирует большинство churn events.

Наибольший объём возвратов связан с причиной `features` — **$1,905.90**, а средний refund наиболее высок для `unknown` — **$18.34** на событие.

При этом наличие причины `features` не доказывает, что именно проблемы с функциональностью являются причиной оттока. Это направление для дополнительного продуктового анализа.

## 5. Изменение тарифов и реактивации

Среди churn events:

* после upgrade — **123 события (20.5%)**;
* после downgrade — **53 события (8.8%)**.

Эти показатели показывают, что заметная часть churn events происходит после изменения тарифного плана.

При этом данные сами по себе не доказывают причинно-следственную связь между изменением тарифа и последующим churn.

### Реактивации

61 из 600 churn events являются реактивациями.

**Reactivation rate = 10.17%.**

Это показывает наличие отдельного сегмента клиентов, которых потенциально можно возвращать после оттока.

---

## 6. Финансовое влияние churn

Подписки клиентов с churn связаны с:

* MRR — **$2,355,245**
* ARR — **$28,262,940**
* доля от текущего MRR — **23.18%**

При churn rate в 22.00% доля текущего MRR, связанного с клиентами с churn events, составляет 23.18%.

Это указывает на то, что финансовая ценность клиентов с churn несколько выше их доли по количеству клиентов.

При этом данный показатель следует рассматривать как **оценку финансового воздействия на основе связанных текущих подписок**, а не как фактически потерянную выручку.

Для точного расчёта финансового эффекта необходимо учитывать MRR непосредственно на дату churn и период после оттока.

## 7. Анализ продукта

Использование функций продукта показывает относительно равномерное распределение активности.

Количество ошибок по функциям находится примерно в диапазоне:

**4.71%–6.56%** от количества использований.

Наиболее высокий error rate:

* Feature 4 — **6.56%**

Наиболее низкий:

* Feature 20 — **4.71%**

Разница показывает потенциальную область для дополнительного анализа качества отдельных функций продукта.

При этом `features` является наиболее распространённой зарегистрированной причиной churn events, поэтому продуктовую аналитику следует использовать совместно с анализом поведения клиентов перед churn.

Особенно важно проверить:

* снижение использования отдельных функций перед churn;
* ошибки при использовании ключевых функций;
* отсутствие использования важных функций;
* связь product engagement с последующим churn.

Таким образом, приоритет обращения не показывает существенного различия в удовлетворённости клиентов.

Для дальнейшего анализа целесообразно проверить связь между обращениями в поддержку, временем решения, эскалациями и последующим churn.

## 9. Результаты статистического анализа

Для проверки потенциальных факторов churn использовались χ²-тест независимости и Mann–Whitney U test.

| Фактор                 | Тест           |    P-value | Результат                       |
| ---------------------- | -------------- | ---------: | ------------------------------- |
| Тариф                  | Chi-square     | **0.9993** | Значимой связи нет              |
| Отрасль                | Chi-square     | **0.0657** | Значимой связи нет при α = 0.05 |
| Страна                 | Chi-square     | **0.6588** | Значимой связи нет              |
| Размер клиента (seats) | Mann–Whitney U | **0.6919** | Значимого различия нет          |
| MRR                    | Mann–Whitney U | **0.6317** | Значимого различия нет          |

### Статистический вывод

Ни один из проверенных факторов не продемонстрировал статистически значимой связи с churn при уровне значимости **α = 0.05**.

Наиболее близкий к порогу значимости результат получен для отрасли (`p = 0.0657`), поэтому сегмент DevTools представляет интерес для дополнительного исследования.

Отсутствие статистической значимости не означает отсутствие бизнес-различий. Оно означает, что на основании имеющейся выборки недостаточно статистических оснований для уверенного утверждения о наличии зависимости.

## 10. Основные бизнес-инсайты

### 1. Churn является существенной бизнес-проблемой

Каждый пятый клиент находится в статусе churn.

**Churn rate = 22%.**

### 2. Тариф не является очевидным рычагом снижения churn

Churn практически одинаков для всех тарифов.

Поэтому простое изменение тарифной структуры не выглядит очевидным способом решения проблемы оттока.

### 3. Product experience требует внимания

Причина `features` является наиболее распространённой зарегистрированной причиной churn events — **19%**.

Следует изучить:

* какие функции используют churned customers;
* какие функции используются реже перед churn;
* какие функции имеют повышенный error rate;
* существует ли связь между отсутствием использования ключевых функций и последующим churn.

### 4. DevTools — приоритетный сегмент для дополнительного анализа

Churn в DevTools составляет **30.97%**, что заметно выше общего уровня 22%.

Хотя статистический тест не подтвердил значимость на уровне 5%, сегмент достаточно выделяется, чтобы провести дополнительное исследование.

### 5. У бизнеса есть возможность работать с реактивацией

Reactivation rate составляет **10.17%**.

Следует изучить характеристики клиентов, которые возвращаются после churn, и использовать их для формирования win-back стратегии.

### 6. Финансовый эффект churn существенный

Текущие подписки клиентов с churn events связаны примерно с **$2.36 млн MRR** и **$28.26 млн ARR**.

Поэтому приоритетом должны быть не только снижение количества churn, но и сохранение клиентов с высокой финансовой ценностью.

При этом эти значения нельзя интерпретировать как фактически потерянную выручку без анализа MRR непосредственно на дату churn.

## 11. Рекомендации

### 1. Провести продуктовый анализ churn

Исследовать использование функций перед churn и определить:

* какие функции не используют уходящие клиенты;
* какие функции имеют высокий error rate;
* какие функции наиболее важны для удержания клиентов;
* как изменяется product engagement перед churn.

### 2. Провести отдельный анализ DevTools

Разделить клиентов DevTools по:

* MRR;
* количеству seats;
* использованию функций;
* обращениям в поддержку;
* причинам churn.

Цель — понять, почему churn в этом сегменте выше среднего и какие характеристики стоят за этим различием.

### 3. Разработать win-back сегментацию

Использовать реактивированных клиентов для определения характеристик успешного возврата.

Отдельно анализировать:

* причину первоначального churn;
* длительность периода до реактивации;
* тариф после возвращения;
* MRR до и после реактивации.

### 4. Создать систему раннего выявления риска churn

Для будущей модели churn можно использовать:

* снижение использования продукта;
* рост количества ошибок;
* обращения в поддержку;
* снижение satisfaction score;
* downgrade;
* отсутствие активности;
* изменения MRR.

### 5. Приоритизировать клиентов по финансовой ценности

Для retention-кампаний следует учитывать не только вероятность churn, но и потенциальный финансовый эффект.

Приоритет можно рассчитывать как комбинацию:

**Churn probability × MRR**

Это позволит сначала работать с клиентами, уход которых несёт наибольший потенциальный финансовый риск.

---

## 12. Итог проекта

Анализ показал, что churn в SaaS-продукте составляет **22%**, а текущие подписки клиентов с churn events связаны примерно с **23% текущего MRR**.

При этом стандартные клиентские характеристики — тариф, страна, размер клиента и MRR — не показали статистически значимой связи с churn.

Таким образом, высокий churn не объясняется одним очевидным клиентским фактором.

Наиболее интересными направлениями для дальнейшего анализа являются:

1. использование функций продукта;
2. ошибки и качество продукта;
3. сегмент DevTools;
4. причины и характеристики обращений в поддержку;
5. поведение клиентов непосредственно перед churn;
6. реактивации и win-back.

Основной следующий шаг для бизнеса — перейти от анализа уже произошедшего churn к **предиктивному выявлению клиентов с повышенным риском оттока** и приоритизации retention-мер по потенциальному финансовому эффекту.

Это позволит перейти от ретроспективного анализа churn к более практической системе управления удержанием клиентов.
